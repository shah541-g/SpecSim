
### Client Agent

An LLM-powered persona with a business context, communication style,
goals, and constraints. It receives only a **natural-language,
need-to-know view** of hidden facts — never the structured requirement
matrix — so it cannot accidentally dump requirement IDs or leak the
evaluation ground truth into the conversation. It reveals information
only when a developer's question is genuinely relevant, stays
realistically vague otherwise, and never invents facts that contradict
the hidden truth.

### Evaluator Agent

A separate LLM call, independent from the Client Agent, that receives
the **complete hidden requirement matrix**, the full transcript, and an
explicit rubric. It classifies each requirement as DISCOVERED,
PARTIALLY_DISCOVERED, or MISSED, flags unsupported assumptions, scores
question quality, and returns strict structured JSON. A deterministic
keyword-based fallback exists only as a last-resort safety net for
total model failure — never as a second scoring path for a successful
LLM call. Every evaluation result carries an explicit
`evaluationMode: "llm" | "fallback"` field so no result can be silently
mistaken for genuine agentic output.

### Why two agents, not one

A single LLM would have to simultaneously roleplay a client and
objectively judge the person talking to it — blurring the very
separation that makes the evaluation meaningful. Splitting the roles
keeps the Client Agent's persona consistent and the Evaluator Agent's
judgment grounded in a ground truth the client never directly exposes.

### Ground truth

Each scenario's hidden requirement matrix (8–10 requirements with
category, priority, and evidence criteria) is deterministic, versioned
JSON — not generated by either agent. It is the fixed benchmark both
agents operate on top of, which is what makes the evaluation
reproducible.

## Baseline

The baseline is a single, general-purpose LLM prompt with no
specialized rubric, no DISCOVERED/PARTIALLY_DISCOVERED/MISSED
taxonomy, and no retry/fallback sophistication — the kind of thing a
developer would build with minimal effort. It receives the same hidden
requirement matrix and the same transcript as the final pipeline, so
the comparison is fair.

## Evaluation Method

**Primary metric: Requirement Discovery Coverage** — the percentage of
hidden requirements the developer's conversation actually surfaced,
judged against the deterministic ground truth.

Six scenarios were used, covering distinct business domains: pharmacy
management, restaurant POS, gym management, hospital appointments,
freelance marketplace, and multi-branch retail (deliberately the most
complex, with 10 hidden requirements and overlapping operational,
pricing, and branch-control constraints). Each scenario's conversation
was generated by running the same fixed set of 7 generic "thorough
developer" questions through the real Client Agent, then evaluating
the resulting transcript with both the baseline and the final pipeline.

A **challenging/weak case** was also run against the multi-branch-retail
scenario: a shallow, UI-only conversation ("what should it look like?",
"can we just make it modern?") to confirm the evaluator correctly
reports near-zero coverage when discovery genuinely fails, rather than
inflating scores.

The final pipeline outperformed the baseline in 5 of 6 scenarios, with
the largest gains on operationally dense domains (gym management,
restaurant POS) where the structured rubric and full ground truth let
the evaluator credit evidence a generic prompt missed or under-counted.
The weak-conversation case confirms the evaluator correctly collapses
to near-zero coverage when no real discovery happens — it isn't simply
rewarding activity.

a failure to hide.

## Main Failure Mode

The single biggest reliability risk in this system was **silent
degradation to a lower-quality result without it being obvious**:
truncated LLM responses that still parsed as partial JSON, and a
keyword-based fallback that could produce plausible-looking (but
non-agentic) scores when the real model call failed. Both were fixed
by (1) explicitly tagging every evaluation with `evaluationMode: "llm"
| "fallback"` so no result can be mistaken for genuine agentic output,
and (2) treating truncated responses as retryable errors rather than
partial successes.

## Hot Take

**A generic evaluator is only as good as the specificity of the
conversation it's judging — and the failure mode is silent, not
loud.** On freelance-marketplace, our fixed 7-question interview
script under-performed the baseline because the questions ("what
reporting do you need?", "what other tools does this need to work
with?") are tuned for operational businesses with physical inventory
and transactions, not for a trust/reputation-driven marketplace where
the real hidden requirements (escrow, dispute handling, reputation
mechanisms) need domain-specific questions to surface. The system
never *told* us this was happening — it just produced a lower number.
The lesson: an agentic evaluation pipeline needs to be paired with
domain-aware question generation, or explicitly flagged as
"generic-question mode," because a single fixed interview script does
not transfer evenly across business domains, and nothing in the
architecture surfaces that mismatch on its own.

## Reproduction Guide

### Requirements
- Node.js 18+
- A Groq or Gemini API key (free tier; see `.env.example`)

### Setup
```bash
npm install
cp .env.example .env
# Edit .env with your API key, e.g.:
# LLM_PROVIDER=gemini
# LLM_API_KEY=<your-key>
# LLM_MODEL=gemini-3.6-flash
# LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai
```

### Run the app
```bash
node server/app.js
```

### Run the baseline vs final comparison for one scenario
```bash
node scripts/run-scenario-conversation.js <scenario-id>
node scripts/run-baseline.js experiments/baseline-vs-final/transcripts/<scenario-id>.json <scenario-id>
node scripts/run-final.js experiments/baseline-vs-final/transcripts/<scenario-id>.json <scenario-id>
```

### Run the full batch and regenerate the report
```bash
node scripts/run-all-experiments.js
node scripts/generate-report.js
```

### Expected output
`experiments/baseline-vs-final/report.md` with a scenario-by-scenario
baseline vs. final comparison table, plus raw results in
`experiments/baseline-vs-final/results.json`.

### Runtime & cost
Each scenario (conversation + baseline + final evaluation) takes
roughly 1–2 minutes on the free tier due to intentional rate-limit
pacing. All testing in this project used free-tier API keys (Groq
and Google AI Studio/Gemini) — $0 cost.

### Limitations
- The 6 scenarios use a fixed, generic 7-question interview script
  rather than domain-adaptive questioning (see Hot Take).
- Free-tier daily token quotas can interrupt long batch runs; the
  scripts support `--resume` to continue from a checkpoint.
